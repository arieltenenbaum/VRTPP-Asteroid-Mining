## What This Notebook Does

Iterative MILP-NLP algorithm for asteroid mining route optimization:
1. **MILP** (Gurobi): selects optimal spacecraft routes given fixed mass ratios (delta-v costs)
2. **NLP** (scipy trust-constr): refines trajectory timing (T_d, T_t) per segment via Lambert's problem, updating mass ratios
3. Repeats until delta-v matrix converges per Eq. 47: `||dv_old - dv_new||_F / max(dv_old) ≤ ε_c`

## Complete List of All Bugs Fixed

### Bug 1 — Mass constraints had cargo term y[k,i] on wrong legs (CRITICAL)
**Cell 18** | Paper Eqs. 41–42  
Ending-base legs must carry the cargo term. Before: on intermediate legs. Fixed.

### Bug 2 — y[k,i] linearization activated on any outgoing arc, not just ending-base arc (SIGNIFICANT)
**Cell 18** | Paper: y_ki = q_i * x^k_{i,k'(k)}  
Before: y[k,i] could activate for any arc leaving i. After: only for the ending-base arc. Fixed.

### Bug 3 — NLP used L-BFGS-B with artificial 3 TU departure cap (SIGNIFICANT)
**Cell 14** | Paper Sec. IV.B.2: only lower bound T_d ≥ T_a + T_s  
Before: `L-BFGS-B`, `[T_d_min, T_d_min+3]`. After: `trust-constr`. Fixed.

### Bug 4 — Convergence denominator was Frobenius norm, not max element (MODERATE)
**Cell 24** | Paper Eq. 47: divide by `max(dv_old)`, not `||dv_old||_F`. Fixed.

### Bug 5 — Hard constraint forced 1 spacecraft (MODELING)
**Cell 18** | Removed artificial `sum(x) ≤ 1` constraint.

### Bug 6 — trust-constr res.success=False blocked valid NLP solutions (SIGNIFICANT)
**Cell 14** | scipy known behaviour: success=False even with a good solution when gradient tolerance not met. Now only checks `res.fun < 100.0`. Fixed.

### Bug 7 — Same-body arcs given mr=0.999 in initialization (CRITICAL)
**Cell 21** | `initialize_mass_ratios`  
Before: `mass_ratios[(i,j)] = 0.999` for same-body pairs. Made Bennu→Bennu virtual hops look nearly free, corrupting MILP from iteration 1.  
After: same-body pairs use `continue` — not added to mass_ratios at all.

### Bug 8 — Same-body arcs created as MILP variables (CRITICAL)
**Cell 18** | `build_milp` V→V arc creation  
Before: `if i != j:` — created arc variables for Bennu(node 9)→Bennu(node 11), etc.  
After: `if i != j and node_to_body[i].name != node_to_body[j].name:`. Also passes `node_to_body` as parameter.

### Bug 9 — Convergence check used full dv matrix including stale off-route arcs (MODERATE)
**Cell 24** | Off-route arcs from previous iterations inject noise.  
After: convergence check restricted to `current_arc_set` (arcs active in current route only).

### Bug 10 — T_service incorrectly applied at Earth departure (MODELING)
**Cell 14** | `optimize_segment` | commit `547763a`  
Paper Eq. 44: service time = mining/refueling hold at **asteroid** nodes only. Earth is the base depot — no hold before departure.  
Before: `T_d_min = T_arrival_i + T_service` for every node including Earth.  
After: `service = T_service if body_i.name != "Earth" else 0.0`. Earth departures now have `T_d_min = T_arrival_i` (= 0 for the first leg).

## NLP Stability Fixes (algorithm stability, not modeling bugs)

### What was tried and removed: Arc Freezing
**commit `efeaf60` added, `b29c5d9` removed**  
Arc freezing (skip NLP re-run for arcs stable across 2+ consecutive iterations) was introduced to stop oscillation, but caused a worse bug: arcs optimized in a long route chain (T_arrival ~35 TU) were frozen into short chains (T_arrival ~5 TU), locking in 30-TU asteroid wait times permanently. Removed entirely.

### What remains (Fixes 1–3):
1. **T_d + T_t warm-start** — `optimize_segment` takes `T_d_prev`/`T_t_prev`, starts the solver from the previous iteration's result
2. **Tighter tolerances** — `gtol=1e-8, xtol=1e-8, maxiter=500` — solver commits to a precise local minimum
3. **Active-arc convergence** — convergence check only on arcs in the current route (see Bug 9)
4. **T_d_max = T_d_min + 5.0** — caps asteroid wait time to ~8 months; prevents NLP from finding low-dv windows requiring year-long stays. Workaround for missing time-window constraints (future feature).

**Discrepancy vs paper (9.18 vs 9.4):**

Our warm-start begins near the Hohmann time (~4.4 TU) and the optimizer settles in that local minimum, never exploring T_t ≈ 6 TU. This makes FG3 look expensive, and the MILP routes away from it after iteration 1.

## Known Remaining Issues

### Issue A — Route comparison is order-sensitive (causes phantom "route changed")
**Cell 24** | `solve_vrtpp_pr` convergence check  
`any(r1 != r2 for r1, r2 in zip(routes, prev_routes))` compares spacecraft in list order. Gurobi can return the same physical routes with Spacecraft 1 and 2 swapped — this counts as "changed" and wastes a full iteration. Also: different virtual base nodes (Earth_B0 vs Earth_B1) for the same physical route count as changed.  
**Fix:** Compare routes as a frozenset of body-name tuples, independent of spacecraft label and virtual node index.  
**Impact:** ~10–15 wasted iterations per run. Not blocking convergence, but doubles runtime.

### Issue B — NLP local minima (suboptimal arc solutions)
**Cell 14** | `optimize_segment`  
trust-constr finds the local minimum nearest to the warm-start. For some arcs (Earth→FG3, Anteros→Earth) there are multiple local minima and the solver doesn't always find the best one. The warm-start from the prior iteration's T_t can bias the solver away from better windows.  
**Potential fix:** Multi-start — try 3–5 evenly spaced T_t seeds (e.g., 2, 4, 6, 8, 10 TU) on the first iteration per arc, keep the best. After that, warm-start normally.  
**Impact:** Would likely recover the Earth→FG3 ≈ 9.51 km/s window and potentially push the objective from 9.18 toward 9.4+.
